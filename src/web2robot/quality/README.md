# quality — 流水线第 1 步:原始网络视频的质量筛选与路由打标

```
海量抓取的视频 → 【本模块】质量筛选 + 打标 → 第2步 技术路由 → 第3步 重定向(EgoInfinity + M7) → 训练数据
```

在**原始 RGB 视频**上跑,不需要任何重建结果。输出**不是二元合格/不合格**,而是判决 + 第 2 步
路由所需的标签。

## 装什么都不用装

```bash
cd <仓库根>            # web2robot/
PYTHONPATH=src envs/rt_env/bin/python -m web2robot.quality \
    data/videos/ --out outputs/qc.jsonl --viz outputs/qc_evidence/
```

依赖只有 `torch` / `torchvision` / `cv2` / `ffmpeg` / `ultralytics`,`rt_env` 里全都现成。
姿态模型权重(226MB)首次运行自动下到 `assets/weights/`(已 symlink 到之前下好的那份,不会重下);
手部检测器权重直接用磁盘上已有的 `external/HaWoR/weights/external/detector.pt`(与
`external/EgoInfinity/pretrained_models/detector.pt` 同一个文件,即官方预筛用的那个)。
路径全部来自 `configs/paths.yaml`,代码里不写死。**没有 pip 安装,没有改动任何共享环境。**

常用开关:

| 开关 | 作用 |
|---|---|
| `--source scraped\|official\|selfcap` | 来源标签。它决定哪些判据能算(自采片内参是占位值) |
| `--n-frames N` | 每段采样帧数**下限**(默认 24;长片按时长自动加密,上限 96) |
| `--hand-weights P` | 换手部检测器权重(默认自动找磁盘上的 `detector.pt`) |
| `--keep-duplicates` | 不丢重复上传(默认按内容指纹去重) |
| `--no-early-exit` | 即使已判 reject 也把所有信号算完 —— **标阈值时用这个** |
| `--viz DIR` | 出带骨架 + 手框标注的证据帧 + 拼版(人工抽检用) |
| `--device cuda:3` | 指定卡;默认自动挑显存最空的 |

启动时会打印手部检测器有没有加载成功。**加载失败不会静默降级** —— 那种情况下"只有手"这条
边界根本量不出来,相关片段一律出 `unknown` 交人工,不会被拒。

## 判决集:五种,不是两种

| 判决 | 含义 | 下游动作 |
|---|---|---|
| `accept` | 第三人称、拍到躯干和双臂,无致命切镜 | 直接进第 2 步路由 |
| `trim` | 同上,但中间有切镜 | 裁到 `usable_span` 再进 |
| `defer` | **手检到双手、但没有躯干** | 交第 2 步判第一/第三人称,**不是淘汰** |
| `reject` | 手检不到稳定的双手(单手从边缘伸入、空镜) | 淘汰 |
| `unknown` | 判决所需信号算不出来(如手部检测器加载失败) | **标记人工看一眼**,不淘汰 |

`defer` 这一档是设计核心。用身体取景**分不开**"第一人称"和"俯拍第三人称手部特写"——两者都是
手在画面、躯干在画外。而**第一人称是第 2 步的一条有效路线**,不是废片。所以这里做二元判断会
把第一人称分支的输入全部饿死。

`unknown` 不淘汰这条来自决策 3(2026-08-05):样本还太少,一遇信息不全就拒会冤枉能用的片。
代码里 `None` 和 `[]` 严格区分 —— 前者是"不知道",后者是"知道且为空"。

## 两个判据用两个模型:边界不同,可信的仪器也不同

三分类的两条边界**不能用同一个模型判**,这是实测出来的,不是设计偏好:

| 边界 | 用什么判 | 依据 |
|---|---|---|
| 是不是 `third_person_body` | **身体姿态模型**(KeypointRCNN) | 全身是它的训练分布,`cup_SUDRM` 实测 0.83 且看图确认 |
| `hands_only` 还是 `no_stable_hands` | **手部检测器**(WiLoR 的 YOLO `detector.pt`) | 姿态模型的手腕关键点在这条边界上**是反的**,见下 |

### 姿态模型数不了手(反例实测,2026-08-05)

用构造法做的配对对照:`neg_onehand` 把右半边涂黑(最多只能看见一只手),`pos_twohands` 是
**同一段素材原样**。结果:

| 检测阈值 | `pos_twohands`(2 只手) | `neg_onehand`(1 只手) |
|---|---|---|
| 0.7 | both_wrist **0.21** | both_wrist **0.25** |
| 0.3 | 0.29 | 0.33 |
| 0.1 | 0.29 | 0.38 |
| 0.05 | 0.29 | 0.38 |

**单手那个在每个阈值下都更高** —— 信号是反的,不是噪声大,所以**没有任何阈值能救**。
原因清楚:KeypointRCNN 是人体检测器,一对脱离身体的手在它的设计范围之外,它既会漏掉明明
在画面里的手,也会凭空补出一个不存在的手腕。所以这里没有"调参",是**换仪器**。

换成手部检测器,同样的对照分得干干净净:

| 片段 | 真值 | 姿态 both_wrist | 手检 `both_hand` |
|---|---|---|---|
| `pos_twohands` | 双手 | 0.21 | **0.42** |
| `neg_onehand` | 单手 | 0.25 | **0.00** |
| `neg_noperson` | 无手 | 0.00 | **0.00** |
| `cand_knit` | 双手 | 0.42 | 0.72 |
| `cup_SUDRM` | 双手 | 0.96 | 1.00 |

`both_hand_rate_min=0.25` 落在一条 0.38 宽的空隙里(通过的最低是 `fold_uz6` 0.38,不通过的
最高是 0.00),是本模块继 `kpt_score_thresh` 之后第二有实测支撑的数。

`both_wrist_rate` 现在仍然报,但**不参与任何判决**,字段也改名成 `wrist_span_est` 以免被误用。

### 一只手被数成两只:重复框必须合并

检测器会对同一只手开两个框 —— 实测同一帧里 2 只手报出 3 个框、涂黑版的 1 只手报出 2 个框。
`both_hand` 是数框的,所以一个重复框就是一只幽灵手。重叠度把两种情况分得没有中间地带:

- **真的两只手**:实测 10/10 对 IoU **= 0.00**(两只手不可能占同一片像素)
- **同一只手的重复框**:IoU **0.20 / 0.24**

`hand_iou_merge=0.10` 取在这条全空区间中间,合并后保留置信度高的那个。效果:`neg_onehand`
的 `both_hand` 从 0.04 → **0.00**(与真值完全一致),`cand_cards` 从 0.89 → 0.48(清掉 39 个
重复框),`cup_cpvH8` 0.50 → 0.43。**10 段的判决一个都没翻**,只是数变干净了。

故意**不**把手数上限设成 2:第三人称画面里可能真有旁观者的手。跨人数错手是另一条已记录的
局限(见下 §已知局限 1),不是这里的问题。

## 取景判据(宽松版,由用户 2026-08-05 定)

**双手关键点 + 双肘关键点 + 至少 1 个躯干关键点(肩或髋)。头部不要求。**

这条判据只用于**第三人称那条边界**(`body_frame_rate`)。"只有手"那条边界不用它,理由见上一节。

```
COCO-17:  0鼻 1左眼 2右眼 3左耳 4右耳 | 5左肩 6右肩 | 7左肘 8右肘 | 9左腕 10右腕 | 11左髋 12右髋 | ...
必需:                                    ≥1 个        两个        两个
不看:    ←──────── 全部不参与判定 ────────
```

为什么不要头:实测 `cand2_AZp` 有一帧 `head=5/5 torso=4/4` 却 `wrist=0/2`,完全不可用;
反过来 `cup_SUDRM` 大量帧 `head=0/5`(相机没拍到头)却完全可用。**头部不携带可用性信息**,
把它设成必需项只会误杀"相机没拍到头但拍全了双手和躯干"的素材。

### 两条通过路径:整片比例 **或** 连续可用段

三分类不是只看整片比例。**任一类都有两条路可以走:整片通过率达标,或者存在一段足够长的连续
可用片段(≥ `min_usable_sec`=5s)。**

这条不是设计洁癖,是第一次跑完看图**发现整片比例算错了片子**才加的:

- `cand_knit` 整片双手率 0.38 → 被拒;`cand_cards` 0.42 → 放行。**看图两者是同一类素材**
  (都是纯手部特写的手工/纸牌教程),0.40 这个阈值正好切在中间。
- 更要命的是这个 0.42 本身不稳:同一个 `cand_cards`,采 24 帧得 0.42,采 72 帧得 **0.56**。
  n=24 在 p≈0.5 处的二项标准误就是 0.10,**"0.38 拒 / 0.42 放"这个判决落在它自己的噪声里**。

根因是**整片平均值量的是剪辑、不是素材**:抓来的视频是成品剪辑,一个 230s 的教程里有 60s 手部
操作 + 170s 产品特写和字卡,平均值很低但可用内容不少。所以现在:

1. **采样密度随时长走** —— `n = clip(时长/3s, 24, 96)`,长片不再用 24 帧去估。
2. **同时报连续段** —— `body_span_est_sec`(身体)/ `hands_span_est_sec`(手检),并据此放行。

连续段的两个防过度声明措施:允许段内有 `span_gap_tol`=1 个采样掉帧(真实素材里手会短暂出画),
但要求段内通过密度 ≥ `min_run_density`=0.6 —— 否则 `h.h.h.h` 这种忽有忽无会被算成"一整段
可用",实际只有一半时间有手。名字里的 `_est` 是认真的:**采样之间的内容是插值推断出来的,
不是逐帧量出来的。**

## 重复上传要去重

抓来的素材里同一个视频换名字重复出现是常态。手上这 10 个文件里就有 **3 个是别人的逐字节副本**
(`chores_cards_frontal` == `cand_cards` 等),实际只有 7 段不同素材。按路径去重看不出来,而
重复片会让样本量和一切基于它的通过率**凭空放大**。

默认按内容指纹去重:`大小 + 首 1MB + 尾 1MB` 的 md5(在抓取规模下保持每文件 O(1),不读整个
50MB)。丢掉的**会打印也会写进报告**,不静默跳过。`--keep-duplicates` 可关。

## 输出的路由标签(留给第 2 步的接口)

```json
{
  "clip_id": "cup_SUDRM59MIc8.mp4",
  "verdict": "accept",
  "view_class": "third_person_body",        // third_person_body | hands_only | no_stable_hands | unknown
  "camera_motion": "static",                // static -> WiLoR+MoGe ; moving -> HaWoR
  "bg_texture": "rich",                     // rich | poor ; poor 时单目 SLAM scale 会退化
  "suggested_route": "egoinfinity/wilor_moge",
  "route_rationale": ["..."],
  "usable_span": [0.0, 52.06],
  "reasons": [],
  "needs_human_review": false,
  "signals": {
    "framing": {"body_frame_rate": 0.83, "body_span_est_sec": 25.0, "...": "..."},
    "hands":   {"available": true, "both_hand_rate": 1.0, "hands_span_est_sec": 44.0,
                "any_hand_rate": 1.0, "avg_hand_size": 0.0155, "trunc_ratio": 0.0,
                "n_merged": 1},
    "cuts": {"...": "..."}, "camera_motion": {"...": "..."},
    "texture": {"...": "..."}, "blur": {"...": "..."}
  }
}
```

`suggested_route` 是**建议不是决定** —— 规则抄自
[`docs/VIDEO_SELECTION_GUIDE.md`](../../../docs/VIDEO_SELECTION_GUIDE.md) §0.1
(HaWoR 需要视差 + 纹理 + 时长**三者齐备**,缺一即退回 WiLoR+MoGe),最终判定权在第 2 步。
那份文档 2026-08-21 从 `hand2robot/` 搬进本仓库,并把准入判据改写成了 §V1–§V4
(连续性 / 人体位置 / 人体朝向 / 切镜拆段)。**本模块还没接那四条** —— 现在的 `camera_motion`
只是路由标签,不是准入判据;`trim` 只裁到最长一段,不是 §V4 要的"拆成多段全保留"。
差在哪见 `docs/BACKLOG.md`。

`usable_span` 是**两个约束的交集**:`cuts.longest_span`(剪辑连续的区间)∩ 连续可用段(手在
画面里的区间,第三人称取 `body_span_est`、只有手取手检的 `hands_span_est` —— 用哪个仪器判的
类,就用哪个仪器的段)。只满足一个都不够,下游要的是"同一个镜头里连续有手"。两者不相交时
不硬凑,打 `span_conflict` 并置 `needs_human_review`,回退到剪辑连续区间(至少保证不跨切镜)。

`signals.framing` 里还存了三个**不参与判决**、专给第 2 步判视角用的量:
`forearm_frac_med`(小臂在画面里的相对长度,近景/第一人称代理)、`elbow_at_bottom_rate`
(手肘贴下边缘的帧占比,第一人称"自己的胳膊从下方伸入"的特征)、`box_frac_med`。

## 执行顺序与早退

```
0 hygiene      分辨率/时长/fps                        (毫秒级)
1 pose gate    取景完整性 → 是否 third_person_body     (~0.9s/段, GPU)
1b hand gate   手部检测 → hands_only / 废片            (~0.3s/段, GPU,复用同一批解码帧)
                                                       ←── 判 reject 就在这里停
2 shot cuts    ffmpeg scene → 最长无切镜段 → trim
3 camera motion Farneback 背景光流 → static/moving
4 appearance   背景角点密度(纹理)+ 手部 ROI 拉普拉斯方差(模糊)
```

1 和 1b **共用同一批解码帧**,不额外解码;两个模型加起来实测 ~11s/段(含长片 96 帧的那些)。

早退与之前"全算不短路"那条决定**不冲突,它们管的是两件事**:

- **跨阶段早退**:判决已经不可能翻转时,不再花钱。光流跑 24 对帧比姿态那一遍更贵,而对
  "只有一只手从边缘伸进来"的片子测背景纹理毫无意义。
- **阶段内全算**:某段被拒时,`reasons` 列出**所有**未通过项,不是第一项就返回。因为取景与
  视角两类判据的拒绝集是重叠的,只报第一条会把原因归错。

标阈值时用 `--no-early-exit` 关掉早退,让每段都拿到全部信号。

## 阈值的出处

`config.py` 里每个数字都标了来源,只有三种:`[OFFICIAL]` 抄自官方 `action100m_filter`
(100M 规模上调过的)、`[MEASURED]` 有实测支撑、`[GUESS]` 占位无样本支撑。**别把 `[GUESS]`
当成有依据的数**。

唯一margin 很宽、可以放心的是 `kpt_score_thresh=3.0`:实测可见关键点得分 4.4–17.0、
不可见的 −4.9–+2.0,中间一条空带。其次是 `both_hand_rate_min=0.25`(空隙 0.38 宽)和
`hand_iou_merge=0.10`(空隙 0.00–0.20 全空)。`body_frame_rate_min=0.60` 则是 `[GUESS]` ——
7 段实测分离度是 0.83 / 0.31 / 0.00,阈值放 0.4–0.8 结果都一样,所以这个数没被数据钉死。

`reference_run/` 存了这次验证通过的完整输出(`qc.md` / `qc.jsonl` / `contact_sheet.png`)和

## 已知局限(2026-08-05 确认记录,暂不修)

1. **多人场景选人逻辑会误放行。** `pose_gate.select_actor()` 取置信度最高的人框。若画面里
   有个旁观者全身入镜、而真正操作的只是从边缘伸进来的一只手,会挑到旁观者从而误判合格。
   现有 7 段素材里**没有这种情况,所以风险真实但未测**。修法是"挑手腕离检测到的手最近的
   那个人" —— 手部检测器现在已经接进来、跑在同一批帧上,**这个修法已经不要额外成本了**,
   但按用户的决定仍然推后:等真遇到旁观者的案例再改,不凭猜测动。
   同理 `both_hand_rate` 也可能被旁观者的手抬高。
2. **阈值没有精细化。** 第三人称正例只有 1 个视频(`cup_SUDRM`)。攒到更多正面样本再校准,
   现在不假装 `body_frame_rate_min=0.60` 这类数字有依据。
3. **~~权重下载渠道~~ 已不成问题。** 手部检测器不需要下载:`detector.pt` 磁盘上就有两份
   (`HaWoR/weights/external/` 和 `EgoInfinity/pretrained_models/`,同一个文件),
   `ultralytics` 在 `rt_env` / `hawor_env` 里已装好。**本模块全程零安装。**
   (此前记录的"ultralytics 五个环境里都没有"是我查错了。)
4. **`bg_texture` 的阈值 `2.0e-4` 是猜的。** 它针对的失效是真实的(纯色背景把 HaWoR 的
   SLAM scale 打到 ~0.01 且大量 NaN),但那段素材已不在磁盘上,数值无法回测。
5. **第一人称先验未验证。** `forearm_frac_med` / `elbow_at_bottom_rate` 是为第 2 步准备的,
   但手头没有第一人称**原始视频**(`ours_*` 只有重建结果,没有视频文件),所以这两个量
   在真实第一人称素材上的取值范围是空的。
6. **"画面深度范围"本轮没做。** 它需要跑一遍单目深度模型(MoGe),成本比本模块其余全部
   信号加起来高一个量级,且此处未接入。这不是漏掉,是明确推后。
7. **切镜检测在 `scene>0.4` 下漏检严重。** 实测 `cand_cards`(849s 的合辑,画面里明显有
   纯色卡和镜头切换)在 0.4 下检出 **0 个**切镜,在 0.2 下检出 12 个;`cand2_ZKC` 3→12,
   `cup_cpvH8` 5→12。0.4 是 `[OFFICIAL]` 值,官方在 1 亿量级上漏检无所谓,我们样本少则会
   把整段合辑当成一个连续镜头。**暂时保留 0.4 以维持与官方可比**,漏检的后果由
   `usable_span` 取交集这一步部分兜住。要改就得先有一批人工标注的切镜真值。
   (`cand2_AZp` 在 0.2 下仍是 0 个 —— 那段确实是连续推镜,不是漏检。)
8. **去重只抓逐字节相同的副本。** 指纹是"大小 + 首尾 1MB",所以**同一视频的另一次转码
   /另一种分辨率抓不出来** —— 那需要感知哈希(pHash / 关键帧直方图)。抓取规模上重编码
   重复很可能不少见,但现在没样本可校,先把便宜且零误判的那一半做掉。
9. **手部检测器本身的召回只在这 10 段上看过。** 对照分离度很干净(0.42 vs 0.00),但手套、
   强动态模糊、极端俯角这些情况都没测。它是官方 100M 预筛在用的同一个权重,不是我们调的,
   但"官方在用"不等于"在我们这批素材上量过"。

## 和"重建后细筛"的关系(两个阶段,别混)
